I/O shape: average request size read 8KB · write 32KB · merge ratio read 0% · write 0% · flush 0.0/s (average -). Small requests (a few KB) with little merging mean random I/O. Large requests with a lot of merging mean sequential I/O. A flush is the request fsync sends to empty the device cache, so it maps directly to translog cost.

Isolate the cause (1)

WarningDisk latency at Warning level (HDD thresholds) · Latency
Evidence

Why it matters
Write latency delays translog fsync and segment flush, which shows up directly as indexing delay. Read latency delays lookups of segments not in page cache, which shows up directly as search delay.
Action

Hardware team (6)

These items concern disks, the RAID controller, BIOS and firmware. The OS shows only part of their state, so check them with hardware management tools (BMC, controller utility).

WarningBottleneck location: the disk or controller itself is slow (queue has headroom) · Latency
Evidence
Avg queued I/O (aqu-sz) p95 5.0 · device inflight p95 5.0 / total device queue_depth 256 → queue utilization 2%
Why it matters
Few requests are waiting, yet each one is slow. The device's condition is a more likely cause than load. Typical cases are a disk with bad sectors, a RAID rebuild, consistency check or patrol read, and a controller write cache turned off by a battery learn cycle or a battery fault.
Action
Check the kernel log for disk and controller errors first. Then ask the Hardware team to check the RAID controller event log, cache and battery status, and disk SMART status for the same time. Expected device latency: NVMe under 0.5ms, enterprise SSD 1ms or less, HDD 10-20ms.
Source: Queue utilization bands (40%, 80%) are field practice. queue_depth is read from /sys/block/DEVICE/device/queue_depth. Expected device latency per Broadcom KB 424485 (NVMe under 0.5ms, enterprise SSD 1ms or less, HDD 10-20ms)
WarningRAID controller battery or cache protection module is not healthy · Hardware
Evidence
PERC H740P Mini: Degraded
Why it matters
When the battery (or CacheVault/ZMM) is charging or faulty, the controller switches the write cache to write-through to protect data. Every fsync then has to reach the disk, and write latency rises sharply. This also happens briefly during a learn cycle.
Action
Check the battery or cache module state and the learn cycle schedule. If the module is faulty, consider replacing it.
Source: storcli output
WarningES data RAID write cache is running in write-through (configured as write-back) · Hardware
Evidence
sda RAID5 · Current cache NRWTD · Configured WriteBack · Write p95 40.00ms
Why it matters
The configured policy is write-back, but the cache is running in write-through now. This is usually caused by a battery or cache module fault or a learn cycle. On HDD, write latency grows several times over.
Action
Check the battery or cache module state first. If the cache is protected, consider switching to write-back. A policy change affects operations, so do it in a maintenance window.
Source: storcli output. The cache policy is judged from the controller tool (the kernel write_cache value is not used)
WarningSigns of trouble on RAID member drives · Hardware
Evidence
/c0/e32/s2 predictive failure 3 · SMART alert No
Why it matters
Predictive failure, SMART warnings and media errors are signs that a drive is wearing out. Retries slow I/O down, and the drive can eventually fail.
Action
Review replacement of the affected drive with the Hardware team. Load rises during the rebuild after replacement.
Source: storcli output
CautionOnly writes are slow. Check the RAID controller write cache · Latency
Evidence
Write p95 40.00ms vs read p95 8.00ms
Why it matters
A RAID controller accepts writes into a battery-protected (or flash-protected) cache first and writes them to disk later. If a battery learn cycle, a battery fault or a policy change switches the cache to write-through, every fsync has to reach the disk and writes alone slow down sharply. RAID 5/6 adds another cause: a read-modify-write on every write.
Action
The controller query shows the Elasticsearch data logical drive running in write-through. Check the cache and battery findings under 'Hardware' below first.
Source: RAID controller cache behavior (common across vendors) · includes controller tool results
CautionES data is on parity RAID (RAID5) · Hardware
Evidence
sda · Write p95 40.00ms
Why it matters
RAID 5/6 recalculates parity on every write, which causes read-modify-write. Elasticsearch replicas already provide redundancy, so Elastic gives RAID 0 striping as the example for performance.
Action
If write latency is not a problem now, leave it as is. When expanding or rebuilding, consider RAID 0 (or 10) combined with Elasticsearch replicas.
Source: [Elastic official] Tune for indexing speed (RAID 0 stripe)

Elasticsearch admin (1)

Items to fix through Elasticsearch settings and operations.

CautionHDD, but the merge thread count is not the Elastic recommendation (1) · Elasticsearch settings
Evidence
Indices with max_thread_count set to 1: 0 · Devices reported as rotational (source: Kernel): sda
Why it matters
The default is half the number of processors. That suits SSD, but on spinning disks concurrent merges scatter the heads and make things slower. Elastic explicitly says to lower it to 1 in this case.
Action
Consider lowering index.merge.scheduler.max_thread_count to 1. It is a dynamic per-index setting, so no restart is needed. The HDD classification is based on rotational=1 as reported by the kernel. If the media is actually SSD, rerun the analysis with -s ssd.
Source: [Elastic official] Merge settings (default is half the processor count, capped at 4 on 9.3 and earlier and on 8.x. Lower it to 1 for spinning disks)

Estimated ceiling

Without a load test, the most that can be calculated is the "device queue ceiling": the number of requests that can be in flight at once (sum of queue_depth) divided by the average time per request. In practice, per-request time grows with load and the disk itself hits its limit first, so this value is a ceiling that cannot be exceeded, not a level you can reach.

The write cache value is what the device reported to the kernel. RAID controllers sometimes report a battery-protected cache as "write through", so this value alone was not used to judge the controller cache state.

%util is for reference only. Devices that process requests in parallel, such as SSD, NVMe, RAID and shared storage, can have headroom even at 100% %util, so it is not used in findings. aqu p95 is a time average that includes requests waiting in the block layer, so it can exceed queue_depth. inflight p95 is the number of I/Os handed to the device and in progress, so it compares directly with queue_depth. The bottleneck location finding looks at both.
