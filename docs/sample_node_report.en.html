I/O shape: average request size read 8KB · write 32KB · merge ratio read 0% · write 0% · flush 0.0/s (average -). Small requests (a few KB) with little merging mean random I/O. Large requests with a lot of merging mean sequential I/O. A flush is the request fsync sends to empty the device cache, so it maps directly to translog cost.

CriticalDisk latency at Critical level (All-Flash thresholds) · Latency
Evidence
Read p95 14.00ms / avg 14.00ms · Write p95 22.00ms / avg 22.00ms (only intervals with 20+ I/Os counted: 24 read intervals, 24 write intervals)
Why it matters
Write latency delays translog fsync and segment flush, which shows up directly as indexing delay. Read latency delays lookups of segments not in page cache, which shows up directly as search delay.
Action
Check the 'bottleneck location' finding below first. If the Guest queue is the cause, fix it on the server. Otherwise the VMware team has to fix it.
Source: [VMware official] Broadcom KB 389082 (vSAN 7 and 8). Read and write latency in the vSAN performance view is considered normal below 5ms for flash and below 20ms for hybrid. The Caution, Warning and Critical split is field practice. Elastic publishes no official numbers

VMware admin (2)

These settings are outside the VM and cannot be changed from the Guest. Request them with the evidence.

WarningBottleneck location: likely outside the VM (hypervisor, vSAN) · Latency
Evidence
Avg queued I/O (aqu-sz) p95 8.0 · device inflight p95 8.0 / total device queue_depth 64 → queue utilization 12%
Why it matters
Few requests are waiting inside the VM, yet each one is slow. Typical causes are vSAN resync, cache tier saturation, I/O contention from other VMs on the same host, and vSAN network latency. Guest configuration changes will not fix this.
Action
Send the measurement time and this report to the VMware admin, and ask them to check esxtop DAVG/KAVG/GAVG, vSAN performance service latency for the VM and disk groups, and whether a resync is running, all for the same time. Device-level expectations per Broadcom KB 424485 are NVMe under 0.5ms, SSD 1ms or less, HDD 10-20ms. If values exceed this range, look at the backend first.
Source: [VMware official] KB 343323 (formerly 2053145). PVSCSI default queue is 64 (device)/254 (adapter); ring_pages 8→32 and cmd_per_lun 254 are recommended. That a gap between in-guest latency and VM/VMDK-level latency can come from queue exhaustion on a low queue depth controller is from Broadcom 'Troubleshooting vSAN Performance'. Queue utilization bands (40%, 80%) are field practice

Estimated ceiling

Without a load test, the most that can be calculated is the "virtual disk queue ceiling": the number of requests that can be in flight at once (sum of queue_depth) divided by the average time per request. In practice, per-request time grows with load and the vSAN side hits its limit first, so this value is a ceiling that cannot be exceeded, not a level you can reach.

%util is for reference only. Devices that process requests in parallel, such as SSD, NVMe, RAID and shared storage, can have headroom even at 100% %util, so it is not used in findings. aqu p95 is a time average that includes requests waiting in the block layer, so it can exceed queue_depth. inflight p95 is the number of I/Os handed to the device and in progress, so it compares directly with queue_depth. The bottleneck location finding looks at both.
